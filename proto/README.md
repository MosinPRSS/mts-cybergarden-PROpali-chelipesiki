# Контракт сводки инцидента

`generate.proto` описывает unary RPC `GenerateIncidentSummary` и
`GenerateDashboardSummary` сервиса `ai.v1.IncidentSummaryService`.
Backend выступает клиентом, сервис в `ai/` — сервером. Сервер запускается через
Docker Compose и вызывает DeepSeek по HTTP. Проверки запроса и ответа реализованы;
выборка связанных записей остаётся задачей backend. Инструкция — в `ai/README.md`.

## Что передавать

В `incident` передаётся ровно один основной инцидент из `backend.models.Incident`.
В `related_incidents` — до 10 отобранных backend записей, которые могут помочь
объяснить основной. Пустой список допустим: сводка всё равно должна строиться.
`as_of` фиксирует время, относительно которого модель описывает сроки и историю.

`IncidentSnapshot` повторяет имена колонок БД: описание, продукт и сервис,
команду, статус, приоритет/срочность/влияние, даты, исходные флаги и решение.
Все поля снимка, кроме `state_enum`, переносятся из одноимённых атрибутов модели.
`state_enum` преобразуется явно:

| Значение в БД | Значение protobuf | Исходный `state_id` |
| --- | --- | --- |
| Assigned | INCIDENT_STATE_ASSIGNED | 0 |
| WorkInProgress | INCIDENT_STATE_WORK_IN_PROGRESS | 2 |
| Resolved | INCIDENT_STATE_RESOLVED | 7 |
| Closed | INCIDENT_STATE_CLOSED | 10 |
| Research | INCIDENT_STATE_RESEARCH | 20 |

Числа enum protobuf не являются кодами `state_id`. `Research` означает этап
после решения инцидента. Наличие текста `solution` у активной записи не меняет
её статус. `updated_at` — время изменения строки БД, а не возникновения проблемы.
Время передаётся через `google.protobuf.Timestamp`, с преобразованием в UTC.
Для nullable дат поле отсутствует; для nullable строк и `is_need_up` используется
presence `optional`. Значения `false`, пустая строка и отсутствие различаются.
Правила presence описаны в [документации Protocol Buffers](https://protobuf.dev/programming-guides/field_presence/).
Служебная дата `0001-01-01T00:00:00` уже нормализуется текущей моделью в `None`.

В этот RPC не входят ФИО и логины исполнителя/инициатора, URL, полный
`source_payload`, прежняя `ai_recommendation`, пользовательские теги и служебные
коды, дублирующие переданные значения. Для первой сводки они не нужны.
При этом свободные описания и решения могут содержать внутренние сведения:
транспорт gRPC сам по себе их не обезличивает. Адрес и доступ к модели должны
соответствовать выбранному корпоративному контуру; этот контракт не задаёт
внешнего провайдера.

## Как использовать связанные записи

Backend отбирает контекст до вызова сервиса и передаёт для каждой записи
причины отбора в `relations`:

- `SIMILAR_DESCRIPTION`: сходные симптомы в заголовке или описании.
- `PREVIOUS_SIMILAR_INCIDENT`: сходные симптомы и более ранняя дата регистрации.
- `SAME_PRODUCT` / `SAME_SERVICE`: подтверждённое совпадение продукта или сервиса.
- `SAME_TEAM`: одна команда назначения; это организационный контекст.

У записи может быть несколько причин. `explanation` содержит факты,
обосновывающие отбор. `similarity_score` заполняется только при реально вычисленном
значении от 0 до 1; для совпадения команды или продукта он не требуется.

Приоритет отбора: похожие симптомы, особенно у ранее решённых записей с
заполненным решением; затем совпадение продукта/сервиса и близость по времени.
Одна команда — слабый сигнал, который не должен вытеснять более полезные аналоги.
В исходной выгрузке одинаковые ID продукта/сервиса встречаются с разными
названиями: нельзя считать один ID достаточным доказательством совпадения.

Поля `is_double`, `is_master`, `is_reason`, `is_effect`, `is_root_incident`
сами по себе не содержат ID связанного инцидента. По ним нельзя выдумывать
конкретную связь или общую первопричину. В текущей модели также нет отдельной
истории жалоб: контекстом служат другие доступные записи инцидентов.

Backend применяет те же ограничения доступа, что и для основного инцидента,
исключает его из контекста и удаляет дубликаты. Сервис использует связанные
записи только для сводки основного инцидента и возвращает ID фактически
использованных записей с объяснениями в `related_incidents_used`.
Совпадение команды, похожее описание или прежнее решение не доказывают
общую причину. Предположения и недостаток данных должны быть явно обозначены.
Тексты инцидентов рассматриваются как данные, а не команды модели.

Исторический контекст доступен, пока записи сохранены в БД.
Миграция `0006` отключает прежнее удаление решённых и закрытых записей через
три дня. Уже удалённую историю нужно повторно получить из источника.

## Проверки на границе RPC

Эти ограничения являются частью контракта, но protobuf сам их не проверяет.
Обработчик отклоняет некорректный запрос с `INVALID_ARGUMENT`:

- отсутствуют основной инцидент, его `id`, `submit_date`, `updated_at` или `as_of`;
- статус не задан или неизвестен, шкалы приоритета/срочности/влияния вне 1..4;
- `service_type_id` не равен 10, 20 или 30;
- контекст содержит больше 10 записей, повторяющиеся ID или основной инцидент;
- связанная запись не содержит полноценного снимка или непустой причины связи;
- причина связи неизвестна, объяснение пустое или similarity score не конечен / вне [0, 1];
- `PREVIOUS_SIMILAR_INCIDENT` относится к записи, созданной не раньше основной;
- дата регистрации записи находится после `as_of`.

Ответ содержит сводку только для `incident_id` основного инцидента.
Backend проверяет совпадение ID, непустой текст, допустимость и уникальность
ссылок на контекст, а также эхо `incident_updated_at` относительно отправленного
снимка. Если строка БД успела измениться, результат нельзя без проверки сохранять
как актуальный. Отсутствие аналогов не является ошибкой и не разрешает их выдумывать.

## Проверка и генерация

Из корня репозитория можно проверить синтаксис и получить descriptor set:

```sh
protoc -I proto --include_imports \
  --descriptor_set_out=/tmp/mts-incident-summary.pb proto/generate.proto
```

Для генерации Python-клиента и серверных интерфейсов требуется `grpcio-tools`:

```sh
mkdir -p /tmp/mts-incident-summary-python
python -m grpc_tools.protoc -I proto \
  --python_out=/tmp/mts-incident-summary-python \
  --grpc_python_out=/tmp/mts-incident-summary-python proto/generate.proto
```

Сгенерированные файлы в репозиторий на этом этапе не добавляются.
## Сводки ближайших сроков и просроченных

`GenerateDashboardSummary` используется для обоих экранов через поле `mode`:

- `SUMMARY_MODE_UPCOMING`: до 20 активных записей с `as_of < deadline <= as_of + window_minutes`;
  возвращаются пояснения строго для первых трёх в порядке запроса.
  `window_minutes`: 30, 60, 120, 360, 720 или 1440 минут; 0 означает 30 для совместимости.
- `SUMMARY_MODE_OVERDUE`: пакет до пяти активных записей с `deadline <= as_of`;
  возвращаются пояснения для всех записей пакета. Backend объединяет пакеты,
  поэтому число карточек в «Ассистенте» не ограничено размером RPC.

Research/Resolved/Closed и отсутствующий deadline в обеих сводках недопустимы.
Порядок UPCOMING после отбора в выбранный период: влияние по убыванию,
дедлайн по возрастанию, приоритет, дата регистрации и ID.
Порядок OVERDUE: влияние по убыванию, дедлайн по возрастанию (дольше
просроченные выше), приоритет, дата регистрации и ID. Полное число
кандидатов и счётчики передаются в `total_candidates` и `statistics`.
Клиент backend обновляется командой `python scripts/generate-ai-proto.py`.
