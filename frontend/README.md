# MTS Incident Command — Frontend

React + Vite интерфейс координатора инцидентов. Данные поступают через HTTP API
и SSE; backend хранит актуальное состояние ITSM.

## Структура

```text
src/
  App.tsx                 # Провайдер зависимостей и вход в приложение
  app/services.ts         # Подключение конкретных браузерных адаптеров
  domain/                 # Модели и правила без React, HTTP и DOM
    incidents/            # Группы, статусы, SLA, фильтрация и сортировка
    notifications/        # События изменения инцидентов
    teams/                # Модели команд и подбор по компетенциям
  application/            # Сценарии приложения и их зависимости
    ports.ts              # Контракты API, подписки, хранилища, звука и lifecycle
    auth/                 # Восстановление, проверка и завершение сессии
    incidents/            # Синхронизация снимков и подтверждённые действия
    notifications/        # История, прочтение и сохранение уведомлений
    analysis/             # Обзор и анализ карточки с отменой запросов
  infrastructure/         # Реализации внешних взаимодействий
    http/                 # Auth/API, HTTP-ответы и проекция ITSM
    browser/              # EventSource, localStorage, аудио и visibilitychange
  presentation/           # Отображение и состояние интерфейса
    pages/                # Вход, оболочка, доска и история
    components/           # Карточки, панели, команды, меню и оповещения
    dashboard/            # Колонки и вычисляемая модель дашборда
    hooks/                # Часы, горячие клавиши, баннеры и toast
  data/                   # Справочники команд и настройки навигации
  lib/, types/            # Совместимые экспорты прежних путей импортов
```

`domain` не зависит от остальных слоёв. `application` использует модели и
контракты, а конкретные HTTP/SSE/storage-реализации выбираются в
`app/services.ts` и передаются через `ServicesProvider`.
Компоненты обращаются к сценариям приложения; прямые вызовы HTTP и localStorage
из интерфейса не используются. Правила зависимостей проверяет
`tests/architecture.test.mjs`.

Новые модули импортируют код из соответствующего слоя напрямую. `lib` и `types`
оставлены как тонкие совместимые экспорты для старых потребителей и тестов;
новой логики в них нет.

## Разработка и проверки

Из директории `frontend`:

```bash
npm run dev
npm test
npm run lint
npm run build
```

Сборка по существующей конфигурации записывается в `backend/dashboard`.
Для отдельной проверочной сборки без изменения этой директории:

```bash
npm run build -- --outDir /tmp/mts-frontend-build
```

Для вывода каждого тестового сценария на Node с поддержкой `--test-isolation`:

```bash
node --experimental-strip-types --test --test-isolation=none tests/*.test.mjs
```

При изменении синхронизации проверьте появление и решение критического,
пересечение групп, Research на координаторах, назначение команды с ошибкой
сервера, обновление после разрыва SSE, вход и выход из аккаунта.

## Размещение карточек

На основной доске три колонки. Инцидент отображается один раз, в старшей
группе: критические → на координаторах → высокий приоритет → исследование.
Цвет карточки определяется той же группой, а остальные группы видны отдельными
метками. Переключателя мультиотображения нет. Исследование доступно отдельной
вкладкой; Research на координаторах остаётся в колонке координаторов.
ИИ-обзор ближайших сроков находится на главной: активные инциденты с остатком
больше нуля и до выбранного срока: 30 минут, 1, 2, 6, 12 часов или сутки
(по умолчанию 30 минут), без просроченных. Сначала влияние, затем ближайший дедлайн.
Выбор передаётся в API и ИИ через `window_minutes`. Страница «Ассистент» в меню
показывает все просроченные активные записи, включая периоды загрузки и ошибки
ИИ. Оба режима используют один компонент, хук и API с параметром `mode`.
