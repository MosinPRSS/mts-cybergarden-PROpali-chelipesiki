# MTS Incident Command — Frontend

React + Vite интерфейс координатора инцидентов. Данные поступают через HTTP API
и SSE; backend хранит актуальное состояние ITSM.

## Структура

```text
src/
  App.tsx                 # Провайдер зависимостей и вход в приложение
  app/services.ts         # Подключение конкретных браузерных адаптеров
  domain/                 # Модели и правила без React, HTTP и DOM
    incidents/            # Группы, статусы, SLA, фильтрация и сортировка
    notifications/        # События изменения инцидентов
    teams/                # Модели команд и подбор по компетенциям
  application/            # Сценарии приложения и их зависимости
    ports.ts              # Контракты API, подписки, хранилища, звука и lifecycle
    auth/                 # Восстановление, проверка и завершение сессии
    incidents/            # Синхронизация снимков и подтверждённые действия
    notifications/        # История, прочтение и сохранение уведомлений
    analysis/             # Обзор и анализ карточки с отменой запросов
  infrastructure/         # Реализации внешних взаимодействий
    http/                 # Auth/API, HTTP-ответы и проекция ITSM
    browser/              # EventSource, localStorage, аудио и visibilitychange
  presentation/           # Отображение и состояние интерфейса
    pages/                # Вход, оболочка, доска и история
    components/           # Карточки, панели, команды, меню и оповещения
    dashboard/            # Колонки и вычисляемая модель дашборда
    hooks/                # Часы, горячие клавиши, баннеры и toast
  data/                   # Справочники команд и настройки навигации
```

`domain` не зависит от остальных слоёв. `application` использует модели и
контракты, а конкретные HTTP/SSE/storage-реализации выбираются в
`app/services.ts` и передаются через `ServicesProvider`.
Компоненты обращаются к сценариям приложения; прямые вызовы HTTP и localStorage
из интерфейса не используются. Правила зависимостей проверяет
`tests/architecture.test.mjs`.

Приложение и тесты импортируют код из соответствующего слоя напрямую.
Инциденты загружаются только из API; локальных демонстрационных записей нет.

## Разработка и проверки

Из директории `frontend`:

```bash
npm run dev
npm test
npm run lint
npm run build
```

Сборка по существующей конфигурации записывается в `backend/dashboard`.
Для отдельной проверочной сборки без изменения этой директории:

```bash
npm run build -- --outDir /tmp/mts-frontend-build
```

Для вывода каждого тестового сценария на Node с поддержкой `--test-isolation`:

```bash
node --experimental-strip-types --test --test-isolation=none tests/*.test.mjs
```

При изменении синхронизации проверьте появление и решение критического,
пересечение групп, Research на координаторах, назначение команды с ошибкой
сервера, обновление после разрыва SSE, вход и выход из аккаунта.

## PWA

Production-сборка содержит manifest, иконки МТС и service worker через
`vite-plugin-pwa`. Приложение устанавливается на HTTPS (для локальной проверки
подходит `localhost`). В браузере с поддержкой установки появляется кнопка
«Установить приложение»; в Safari на iPhone/iPad показывается инструкция через
«Поделиться» → «На экран “Домой”». В режиме `npm run dev` worker отключён.

Кешируется только статическая оболочка текущей сборки. Запросы `/api`, включая
авторизацию и SSE, всегда идут на сервер; ответы, инциденты и действия в офлайн
не кешируются и не ставятся в очередь. При потере сети рабочая область
блокируется сообщением, а открытые окна и введённые значения остаются на месте.

Новая версия ожидает подтверждения кнопкой «Обновить»; «Позже» сворачивает
уведомление. Обновление недоступно при открытом окне назначения или карточке,
во время анализа, входа, сохранения и пока доступна отмена решения. Активация
worker в другой вкладке не перезагружает текущую вкладку автоматически.
Проверка версии выполняется браузером при запуске, при возвращении во вкладку,
после восстановления сети и раз в час. Caddy отдаёт worker, manifest и HTML с
перепроверкой кеша, а файлы с хешами в `/assets` — с длительным кешированием.

Локальная проверка production-режима:

```bash
npm run build -- --outDir /tmp/mts-pwa-build
npm run preview -- --outDir /tmp/mts-pwa-build --host localhost
```

Для проверки входа и инцидентов нужен backend: preview использует тот же proxy
`/api`, что и dev, с адресом `http://backend:8000`. После проверки можно удалить
worker и кеш через DevTools → Application → Service Workers / Storage.
Для критических инцидентов поддержаны системные уведомления браузера (Desktop / Mobile Notification API и Service Worker). В истории уведомлений предусмотрена кнопка включения системных оповещений. Фоновый Web Push при полностью закрытом браузере в эту реализацию не входит.

## Размещение карточек

На основной доске три колонки. Инцидент отображается один раз, в старшей
группе: критические → на координаторах → высокий приоритет → исследование.
Цвет карточки определяется той же группой, а остальные группы видны отдельными
метками. Переключателя мультиотображения нет. Исследование доступно отдельной
вкладкой; Research на координаторах остаётся в колонке координаторов.
ИИ-обзор ближайших сроков находится на главной: активные инциденты с остатком
больше нуля и до выбранного срока: 30 минут, 1, 2, 6, 12 часов или сутки
(по умолчанию 30 минут), без просроченных. Сначала влияние, затем ближайший дедлайн.
Выбор передаётся в API и ИИ через `window_minutes`. Страница «Ассистент» в меню
показывает все просроченные активные записи, включая периоды загрузки и ошибки
ИИ. Оба режима используют один компонент, хук и API с параметром `mode`.
Автоматический ИИ-обзор обновляется раз в две минуты; live-обновления карточек
не отменяют текущий анализ. Неизменённые записи сохраняют свои пояснения,
изменившиеся до нового анализа показываются с подсказками по правилам.
Ручное обновление доступно отдельной кнопкой.

Приоритет и длительность просрочки на странице «Ассистент» фильтруют уже
полученные карточки на клиенте, без дополнительных запросов к ИИ. Счётчик
в меню показывает все активные просрочки независимо от этих фильтров и
обновляется при пересечении дедлайна, решении и новых снимках.

HTTP-снимок после ошибки загружается повторно с задержкой от 1 до 30 секунд.
Успешный SSE-снимок отменяет отложенные повторы; уход со страницы отменяет
запрос и таймеры. Повторная проверка сессии синхронизирует аккаунт, сменённый
в другой вкладке, и пересоздаёт рабочую область для нового пользователя.

Кнопка «Подобрать команду» в карточке вызывает отдельный ИИ-подбор через
`POST /api/incidents/{id}/recommend-team` и gRPC `RecommendIncidentTeam`.
В запросе только профили команд из реестра; инцидент backend читает из БД.
Панель показывает команду, процент соответствия и короткую причину. Оценки
критериев доступны по раскрытию. При сбое LLM эвристическая команда не
показывается; смена версии инцидента отменяет запрос и убирает старый результат.
После подтверждения назначения в БД сохраняется `team_selected_with_ai`, панель
показывает «Выбрано с помощью ИИ» без кнопок подбора, в том числе после перезагрузки.
Если ИИ предложил текущую команду, её выбор также нужно явно подтвердить.
Ручная смена команды снимает отметку и снова позволяет подбор.

В окне привязки команды кнопка «Подобрать с ИИ» или первое включение фильтра
«Только рекомендации ассистента» запускает подбор инцидентов. До ответа модели
эвристические проценты не показываются. Поиск и фильтр используют готовый ответ
без новых запросов. Изменение данных отменяет старый запрос и сбрасывает подбор.
Назначение положительной рекомендации сохраняет отметку выбора с ИИ.

Краткая сводка карточки: проблема и `next_step`, каждое поле — до 180 символов /
24 слов. Даты и SLA в модель не передаются: их показывает карточка по расчётам
системы. Из аналогов допускается максимум один полезный пример; отбор контекста
требует решённого статуса, заполненного решения и релевантности симптомов и сервиса/продукта.

После успешного завершения на 30 секунд появляется уведомление с «Отменить».
Каждое завершение имеет собственное окно; кнопка блокируется на время запроса.
Отмена подтверждается сервером с проверкой версии. После истечения срока
уведомление исчезает. Перезагрузка страницы убирает локальное уведомление.

Решение переводит инцидент в «Исследование ситуации». В карточке исследования
есть постоянная кнопка «Отменить решение · Вернуть в работу» и «Закрыть инцидент».
В истории отображаются только Closed. Карточки и подробности показывают имена
решившего и закрывшего; неизвестные авторы исходных записей не выдумываются.

Состав команд представлен моковым выходом ITSM в `src/data/itsmDirectory.ts`.
ITSM рассматривается как внешний black box: в интерфейс поступают команды,
внешние идентификаторы участников, должности, контакты и состояние дежурства.
Участники справочника не создаются в таблице пользователей и не получают доступ
к сервису. Учётные записи и авторизация остаются только у координаторов.
