# МТС: модель исходной выгрузки ITSM

FastAPI, PostgreSQL, SQLAlchemy asyncio, Alembic и SSE. С версии `0.2.0`
рабочая модель соответствует оригинальным 44 записям `character_problems.json`,
а не прежней демонстрационной структуре.

## Сверка с данными и презентацией

Оригиналы сохранены без редактирования в `fixtures/character_problems.json` и
`fixtures/incidents_attributes.json`. В выгрузке 46 полей; справочник описывает
только 30 из них. Поддерживаются все поля, включая отсутствующие в справочнике.

Справочник и фактическая выгрузка расходятся по `stateId`: описание справочника
связывает 7 с «Закрыт», 10 с «Завершен» и не описывает 20. Все записи самой выгрузки
согласованы следующим образом; модель сохраняет именно эти пары:

| stateId | stateEnum | state | Количество |
| --- | --- | --- | --- |
| 0 | Assigned | Назначен | 14 |
| 2 | WorkInProgress | Выполняется | 10 |
| 7 | Resolved | Завершен | 10 |
| 10 | Closed | Закрыт | 5 |
| 20 | Research | Исследование ситуации | 5 |

Расхождение не исправлялось переписыванием входных файлов. Неизвестные коды или
противоречивые пары `stateId/stateEnum` отклоняются при валидации.

Правила групп вынесены в `domain/incidents.py` и соответствуют четырём группам
в презентации. Активные статусы — Assigned и WorkInProgress; Research — отдельный
этап уже решённого инцидента, который тоже может требовать передачи координаторами.

| Группа | Правило | Записей в оригинале |
| --- | --- | --- |
| Критические | Активный инцидент, `priorityId=4` — наивысший приоритет | 0 |
| На координаторах | Активный или Research; точное назначение на «КЦ ИТ Координаторы Массовых Инцидентов» | 2 |
| Высокий приоритет | Активный инцидент, `priorityId=3` | 1 |
| Исследование ситуации | `stateEnum=Research` | 5 |

Для критических принят наивысший приоритет 4: отдельного признака критичности
в предоставленном формате нет. Высокая срочность `urgencyId=4` не превращает
инцидент в критический. У этой конкретной выгрузки нет ни одной записи с
`priorityId=4`; для проверки такого сценария тесты создают изменённую копию записи.

Один инцидент может попасть в несколько групп: например, критический на
координаторах или Research на координаторах. Группы вычисляются из атрибутов,
не хранятся редактируемым массивом и не меняются вручную. Resolved и Closed
не превращаются в Research. Пустой список групп допустим и не означает Critical.

Особенности исходных данных, учтённые моделью:

- `id`, `sysId`, ID продуктов, сервисов и логины — строки. 18-значные значения
  не переводятся в JavaScript Number и не теряют точность.
- `productName` и `service` — разные поля. В источнике один productId/serviceId
  встречается с разными названиями: поэтому сущности не объединяются автоматически
  по этим ID. На карточке показан продукт, исходный сервис сохранён отдельно.
- `deadline` — абсолютное время с часовым поясом, допускает null (3 записи).
  `serviceId` также nullable (7 записей).
- `waitingExitDate="0001-01-01T00:00:00"` — пустое служебное значение: в типизированной
  колонке хранится null, исходная строка сохраняется в `source_payload`.
- `isNeedUp` сохраняет три состояния: null — 23, false — 20, true — 1. Описанные
  справочником Да/Нет также принимаются, но не смешиваются с неизвестным значением.
- Исполнитель и инициатор — исходные ФИО/логины ITSM. Они не требуют локальной
  учётной записи; импорт не выдаёт людям роли engineer/coordinator.
- Непустой `solution` встречается и у активных инцидентов. Решённость определяется
  статусом, а не этим текстом, приоритетом или наличием даты.
- Остальные флаги, подстатусы, канал регистрации, данные продукта и сервиса
  сохранены как отдельные атрибуты. Дополнительные неизвестные поля не теряются
  благодаря полному исходному JSON в `source_payload`.

## SLA

В рабочей таблице нет уменьшающегося счётчика `sla`. Оставшиеся секунды вычисляются
из `deadline` при чтении. Для активного инцидента отрицательное число означает
просрочку, ноль — истёкший срок. Нет срока — нет выдуманного нуля.

Для Resolved/Closed/Research результат фиксируется относительно `completionDate`,
а не текущего времени. Если дата завершения неизвестна, соблюдение срока не
утверждается. API возвращает `sla_state`: remaining, overdue, met, breached,
no_deadline или unknown. Фронт считает активный таймер по абсолютному дедлайну,
поэтому повторная загрузка данных не сбрасывает оставшееся время.

## Схема и миграции

`0001` — историческая демо-схема. Миграция `0002` сохраняет её инциденты и связи
с пользователями в `legacy_incidents`, затем создаёт новую `incidents` с 46
типизированными атрибутами источника. В новой модели нет обязательной связи
исполнителя с `users`. Таблица пользователей приложения остаётся отдельно.

Есть ограничения диапазонов приоритета/срочности/влияния, допустимых статусов,
соответствия кода статусу и уникальности sysId. Данные старого демо не смешиваются
с оригинальной выгрузкой. Рабочая цепочка миграций находится только в `migrations/`;
исторические ревизии и модель `LegacyIncident` нужны для обновления и отката
существующих БД.

```bash
venv/bin/python -m alembic upgrade head
venv/bin/python -m alembic current
venv/bin/python -m alembic check
```

Обратная миграция `0002 -> 0001` восстанавливает старую таблицу из архива,
удаляя новую таблицу оригинальных записей. Она проверена только на временной
тестовой БД; для рабочей БД обратная миграция не запускалась.

## Импорт

В директории `backend`:

```bash
venv/bin/python -m scripts.seed
# Или другой файл в том же исходном формате:
venv/bin/python -m scripts.seed --path /absolute/path/character_problems.json
# Явно обновить существующие записи исходной выгрузкой:
venv/bin/python -m scripts.seed --update-existing
```

Сначала валидируется весь массив и уникальность id/sysId. По умолчанию seed
добавляет только отсутствующие ID: повторный запуск Docker сохраняет решения,
назначения, даты и версии рабочих записей. Конфликт существующего ID не вызывает
обновление. Для явного обновления выгрузкой используйте `--update-existing`;
`POST /api/incidents` также остаётся upsert. Ошибка откатывает транзакцию.
Неизменённые записи сохраняют время импорта и изменения. ИИ-подсказки и отдельные
пользовательские теги не перезаписываются импортом источника.

Назначение и решение читают запись с `SELECT ... FOR UPDATE` до изменения её
полей и исходного JSON. Блокировка удерживается до commit/rollback. Импорт
блокирует существующие записи по ID в одном порядке перед сравнением данных.
Назначение принимает `team_selected_with_ai` (по умолчанию `false`). После
подтверждения ИИ-команды отметка хранится в БД (миграция `0007`) и возвращается
в снимках и SSE; повторный ИИ-подбор даёт 409 без обращения к модели.
Ручное назначение снимает отметку. Импорт сохраняет её при той же команде и
сбрасывает при изменении `assignedGroupName`.

Повторный запуск на той же выгрузке возвращает 0 созданных, 0 изменённых,
44 неизменённых записи. Команда также сообщает количество сохранённых архивных
демо-инцидентов. Исчезновение ID из файла не вызывает неявного удаления из БД.

Полный исходный объект сохраняется без потерь, включая null, служебные даты и
неизвестные поля. Нормализация применяется только к типизированным колонкам и
основному API-ответу.

Основной ответ сохраняет имена источника camelCase и различает productName/service.

и поля для текущего интерфейса. Фронтенд выполняет небольшую проекцию для карточки,

```bash

```

## Запуск

Настройки читаются из корневого `.env`, затем из `backend/.env`;
переменные процесса имеют приоритет. Используются `DATABASE_URL`/`DB_URL`
или отдельные `POSTGRES_*`. Compose публикует PostgreSQL только на localhost.

```bash
# Из корня проекта после подготовки .env по .env.example:
docker compose up -d --wait db
# Далее из backend:
venv/bin/python -m pip install -r requirements.txt
venv/bin/python -m alembic upgrade head
venv/bin/python -m scripts.seed
venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload --timeout-graceful-shutdown 5
```

## Проверки и оставшиеся этапы

```bash
# Без подключения к PostgreSQL; интеграционные тесты пропускаются:
venv/bin/python -B -m unittest discover -s tests -v
# Полный прогон на отдельной временной БД, которая затем удаляется:
venv/bin/python -B -m scripts.test_database
# Из frontend:
npm test
npm run lint
```

Изменения от ITSM принимаются через `POST /api/incidents` в том же формате,
что и исходные моки. JSON-файл служит примером выгрузки; наблюдатель файла не нужен.
POST и CLI используют общую валидацию. POST сохраняет оригинальный объект,
включая служебные даты и дополнительные поля. Неизменённый повтор не меняет
версию и не запускает повторное SSE-обновление. Изменения через POST, resolve
и assign публикуют полный снимок. Его чтение и публикация используют общие
функции `load_incident_snapshot` и `publish_incident_snapshot` из
`services/incidents.py`; изменения фиксируются до публикации.
CLI-импорт — отдельная команда без SSE.

Миграция `0006` отключает удаление решённых инцидентов через три дня.
История доступна в интерфейсе и используется для поиска похожих случаев.
Уже удалённые старой версией записи миграция не восстанавливает; их можно
повторно импортировать из источника.

На главной три колонки, каждая карточка отображается один раз. Колонка и
оформление выбираются по старшей группе: критические → на координаторах →
высокий приоритет → исследование ситуации. Все группы показаны на карточке.
Исследование доступно отдельной вкладкой; Research на координаторах виден
в колонке координаторов и допускает переназначение.
При переподключении и возвращении во вкладку клиент запрашивает свежий снимок;
уведомления сохраняют все переходы в пакете, включая решение критического.

ИИ: `GET /api/incidents/summary?mode=upcoming&window_minutes=30` — ближайшие сроки
в выбранном периоде: 30, 60, 120, 360, 720 или 1440 минут (по умолчанию 30)
без просроченных (три карточки, контекст до 20 записей);
`GET /api/incidents/summary?mode=overdue` — все просроченные активные инциденты
на странице «Ассистент», анализ пакетами по пять без ограничения списка;
`GET /api/incidents/{id}/summary` — анализ одной карточки с контекстом до пяти
аналогов. Оба метода используют существующий gRPC-сервис. Подробности —
в `../ai/README.md`. Анализ карточки запускается кнопкой, кэш — 5 минут в памяти
одного backend-процесса. Redis и отдельная очередь для MVP не используются.

Задайте `ITSM_URL_TEMPLATE` в корневом `.env`, например
`https://your-itsm.example/incident/{id}`. Поддерживаются `{id}` и `{sysId}`.
Пока адрес неизвестен, кнопка перехода отключена.

SSE работает для одного worker, без истории событий и replay.
Для MVP запускайте один backend-процесс; восстановление соединения выполняет
полную синхронизацию состояния, но не восстанавливает все промежуточные события.

## Вход и начальные аккаунты

Регистрация отключена в интерфейсе и API. При старте бэкенда и при запуске
`python -m scripts.seed` автоматически добавляются пять начальных аккаунтов:

| Логин | Роль |
| --- | --- |
| admin | Координатор |
| coordinator | Координатор |
| engineer1 | Координатор |
| engineer2 | Координатор |
| observer | Координатор |

Для каждого аккаунта сгенерирован отдельный пароль; в
`fixtures/default_users.json` хранятся только хеши. Повторный запуск добавляет
только отсутствующие аккаунты и сохраняет пароли и профили существующих.
Учётные данные передаются отдельно от исходного кода.

`POST /api/auth/login` принимает логин и пароль, `GET /api/auth/me` возвращает
текущего пользователя, `POST /api/auth/logout` отзывает текущую сессию и закрывает
связанные SSE-подключения. Логины регистронезависимы.

Секрет сессии хранится в HttpOnly-cookie `mts_session` (SameSite=Strict,
Path=/api), в таблице `user_sessions` сохраняется только SHA-256 от случайного
секрета. Миграция `0004` применяется обычным `alembic upgrade head` и при старте
приложения. Срок сессии задаёт `ACCESS_TOKEN_EXPIRE_MINUTES` (по умолчанию сутки),
`AUTH_COOKIE_SECURE=true` включает Secure-cookie за HTTPS-прокси. При прямом
HTTPS Secure включается автоматически. При отдельном адресе фронтенда добавьте
его origin в `CORS_ORIGINS`; штатный фронтенд проксирует `/api` с того же origin.

Войти в сервис, читать инциденты и исходные записи, подключаться к SSE,
назначать команды и решать инциденты могут только пользователи с ролью
`coordinator`. Администраторы, инженеры и наблюдатели получают 403, включая
запросы с ранее выданной сессией. Миграция `0005` переводит пять начальных
аккаунтов в координаторов, сохраняя логины и пароли, и отзывает сессии остальных
ролей.
Маршрут `POST /api/incidents` также требует сессию координатора. Генератор
входит с логином `--login` / `MTS_COORDINATOR_LOGIN` и паролем из
`MTS_COORDINATOR_PASSWORD` либо скрытого ввода в терминале. Лимит входа — 20 попыток
в минуту на IP для текущего процесса; SSE и лимитер рассчитаны на один worker.

`POST /api/incidents/recommend-for-team` принимает профиль `TeamCandidate` и
возвращает оценки подходящих активных/Research инцидентов из БД для команды,
включая отказы модели. Уже назначенные команде и подтверждённые ИИ-назначения
исключены. Результат сортируется по проценту, версии перепроверяются после RPC.

Жизненный цикл: `POST /api/incidents/{id}/resolve` переводит активный инцидент
в Research и сохраняет ФИО решившего (`resolved_by`). Время восстановления —
`completionDate`; SLA фиксируется на нём. Решённые записи со статусом Resolved
из источника также показываются в исследовании; история содержит только Closed.

`POST /api/incidents/{id}/close` принимает `{"updated_at":"текущая версия"}`,
разрешён только для Research/Resolved и переводит в Closed. Сохраняются ФИО
закрывшего (`closed_by`) и время `closed_at`, имя решившего остаётся прежним.
ФИО хранятся снимком, поэтому последующее редактирование аккаунта их не меняет.
Миграция `0009` добавляет поля и восстанавливает доступных авторов прежних
решений по журналу. Если автора нет в источнике/журнале, он остаётся неизвестным.

`POST /api/incidents/{id}/undo-resolve` с текущим `updated_at` доступен
координаторам постоянно, пока инцидент в исследовании. Восстанавливает статус
и дату до решения, сохраняя последующие назначения команды и исполнителя.
Для импортированных исследуемых записей без журнала возвращает Assigned.
Закрытые записи не возвращаются этим действием. Изменённая версия даёт 409.
Быстрое уведомление «Отменить» остаётся на 30 секунд, постоянная кнопка —
в карточке исследования. Resolve, отмена и close записываются в incident_actions.
